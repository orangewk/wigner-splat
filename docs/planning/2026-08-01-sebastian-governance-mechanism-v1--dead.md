# セバスチャン責務の機構化案 v1（旧案）

- 状態: dead（後継案へ統合、未実装）
- 後継: [`2026-08-01-sebastian-governance-mechanism--proposed.md`](2026-08-01-sebastian-governance-mechanism--proposed.md)
- 決定者: orange
- 対象: ルーターランナー「セバスチャン」および、引き継ぎで交代する同等ランナー
- 目的: 有益な助言能力を残しつつ、仕様作成・検収・完了裁定の自己承認を防ぐ

## 結論

「管理役」から「執事」への署名変更は、振る舞いを思い出させる認知的なブレーキとして残す。ただし署名だけでは権限を制約できないため、実効的な防止策は **提案と批准を別主体にする二鍵方式** とする。

セバスチャンはリサーチ内容への助言・異常検知・追加調査の提案をしてよい。しかし、自分が作成または変更した仕様・受入条件・主張について、検収者または完了決定者を兼ねない。

## 権限境界

セバスチャンが行ってよいこと:

- タスクの分解、担当への配送、進捗と依存関係の記録
- 証拠の不足、主張の衝突、スコープ逸脱の指摘
- 追加調査・再計算・保留の提案
- 独立検収結果と決定者の裁定の記録

別主体の批准が必要なこと:

- 研究仕様・受入条件・評価指標の確定または変更
- 数式、数値、引用、再現性の検収
- PASS / HOLD / GO / 完了の裁定
- 公開可能性および権威ある主張の更新

## 運用フロー

```mermaid
flowchart LR
    A[主張責任者が仕様と受入条件を凍結] --> B[執事が担当へ配送]
    B --> C[研究・実装担当が成果と証拠を提出]
    C --> D[執事が不足や衝突を助言]
    D --> E[独立検収者が再計算・出典確認]
    E --> F[orange または委任された決定者が裁定]
    F --> G[執事が裁定と根拠を記録]
```

同一人物・同一ランナーが複数の箱を担当してもよいのは、配送・助言・記録の範囲だけとする。仕様作成者と検収者、検収者と最終決定者は、対象主張について独立させる。

## 機械的に検査する記録

各タスクに `PACKET.json` 相当の単一記録を置き、少なくとも次を持たせる。

- `claim_owner`
- `spec_author`
- `implementer`
- `verifier`
- `decision_owner`
- `acceptance_criteria_ref`
- `evidence_refs`
- `audit_ref`
- `decision_ref`
- `authoritative_claim_refs`
- `withdrawn_claim_refs`
- `open_questions`
- `do_not_rederive`
- `known_failures`

予定する検査:

1. `spec_author == verifier` なら検収不可。
2. セバスチャンが仕様または受入条件を変更した対象は、別の検収者を必須とする。
3. PASS / HOLD には `audit_ref`、GO / 完了には `decision_ref` を必須とする。
4. 受入条件は作業開始前に固定し、変更履歴と決定者を残す。
5. 撤回済み主張を権威ある根拠として参照できないようにする。

## 助言の扱い

セバスチャンの内容面への口出し自体は禁止しない。有益な可能性があるため、次の形で「提案」として残す。

- 指摘対象
- 根拠または再現手順
- 確信度
- 推奨する次の検証
- 未批准である旨

助言は、独立検収者または決定者が参照して採用した時点でのみ、仕様・主張・完了判定へ反映する。

## 引き継ぎの要件

問題は今回のランナー固有とは限らず、開始時点から存在する体制と複数回の引き継ぎに由来しうる。したがって人格名やモデル名ではなく役割へ制約を掛ける。引き継ぎ時は、権威ある主張、撤回済み主張、未解決点、再導出しない事項、既知の失敗、誰が何を決められるかを明示する。
